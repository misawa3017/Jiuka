# Jiuka 揪咖 — 產品需求 SPEC

更新日期：2026-11-14
狀態：產品方向已確認；Web 核心流程已有本機實作，正式雲端設定與試用驗證尚未完成。

## 1. 產品定位與目標（已確認）

Jiuka 是協助籃球、羽毛球球友招募打球人數、管理報名並分攤室內場地費的平台。

室內打球需要租借場地，主揪經常遇到人數不足、每人負擔過高及臨時找不到人的問題。產品應讓主揪清楚發布缺額與費用，讓球友找到合適場次並報名。

- 主要使用者：已安排場地、需要補人的主揪，以及尋找籃球或羽毛球場次的球友。
- 商業模式：核心功能免費使用，透過廣告營收維持服務。
- 第一階段：開發 Flutter Web，先驗證核心功能與實際揪團流程。
- 第二階段：在 Web 驗證後開發 iOS，盡量共用 Flutter 介面、業務邏輯與 Firebase 資料。
- 成功目標：主揪能發布缺人場次，球友能完成報名，雙方能確認人數與費用；實際招募效果與廣告收益須由試用及營運資料驗證。

本文件取代原本以一般社交活動、興趣推薦為主的需求方向。舊文件保留於 `requirements.legacy.md`，僅供歷史參考，不作為當前驗收標準。

## 2. 階段規劃

### 第一階段：Web 功能驗證

以手機瀏覽器為主要操作情境，同時支援桌面瀏覽器。使用者透過網址即可開啟，不需安裝 App。

建議的核心流程：

主揪安排場地 → 發布場次與缺額 → 分享連結或從列表找場次 → 球友登入報名 → 額滿候補 → 取消後遞補 → 主揪確認人數與費用。

第一階段先讓上述流程完整可用，再驗證 Web 廣告串接。廣告服務商、正式啟用時間與投放條件尚待確認，不將尚未取得的正式廣告帳號當作功能測試前提。

### 第二階段：iOS

- 沿用 Web 已驗證的帳號、場次、報名、候補及費用管理功能。
- 完成 iOS 平台配置、操作適配、廣告整合與上架準備。
- 通知、平台權限及其他原生能力於第二階段細化，不假設 Web 的整合方式可直接套用。
- Android 不列入目前兩階段的交付承諾。

## 3. 第一階段功能草案

以下為依討論整理的建議範圍；其中費用規則、取消政策及通知方式須在實作前完成第 7 節的決策。

### 3.1 帳號與個人資料

- 第一階段 Web 與第二階段 iOS 均僅提供 Google 登入，沿用 Firebase Authentication；不支援 Email／密碼登入、註冊或密碼重設。
- 建議允許未登入者瀏覽公開場次，發布與報名時要求登入。
- 登入後應能回到原本欲報名的場次。
- Google 單一登入為已確認決策；Email 僅作帳號資料，不作密碼登入入口。
- 首次 Google 登入成功時，以 Firebase UID 建立完整使用者文件，初始暱稱採 Google 顯示名稱；後續登入沿用資料，不覆蓋自訂暱稱。
- 使用者可修改暱稱、登出；取消登入或失敗時顯示提示並可重試，不建立不完整文件。
- 必須等個人資料載入成功才進入已登入頁面；重新整理恢復工作階段，登出後清除 App 登入狀態。
- Firebase 登入供應商僅啟用 Google，停用 Email／Password。既有測試帳號先盤點，不自行刪除或以 Email 合併使用者文件。

### 3.2 發布場次與既有人數

- 場次資訊包含運動類型（籃球／羽毛球）、日期、開始與結束時間、地區、球館／地點、總名額、既有人數、費用及補充說明。
- 主揪可選填活動名稱（最多 40 字），列表與詳情以活動名稱為標題；未填時以球館名稱為標題。
- 列表與詳情顯示主揪暱稱（公開）。暱稱存於場次 `organizerName`，規則要求等於主揪自己的暱稱；主揪改暱稱時同步自己所有場次。舊場次在主揪編輯場次或改暱稱後補上。
- 主揪已找好的朋友應能占用名額，不必要求所有朋友先註冊。
- 例：總名額 10 人、既有 6 人時，只招募剩餘 4 人。
- 名額計算須避免將主揪、既有朋友與 App 報名者重複計入；主揪是否出席須有明確表示方式。
- 必填欄位、時間先後、過去時間及人數範圍須驗證；既有人數不得超過總名額。
- 建議允許獨立發布單場活動，球隊／團體作為選用關聯，報名不強制先加入球隊。

### 3.3 找場次與分享

- 顯示可報名的未來場次，依開始時間由近到遠排列。
- 提供運動類型、地區及日期篩選。
- 列表清楚顯示時間、地點、缺額及費用；詳情顯示報名條件與候補狀態。
- 每個場次提供可分享的網址；直接開啟或重新整理網址仍可進入對應頁面。
- 已取消或已開始的場次不得繼續接受新報名。

### 3.4 費用分攤

- 報名前必須清楚顯示收費方式及金額，區分「確定費用」與「預估分攤」。
- 首版同時支援「每人固定費用」與「輸入整場場租並顯示每人預估分攤」兩種方式；此選擇已確認。
- 若採依人數分攤，須先決定計費人數、主揪是否分攤、既有朋友如何計入、取整方式、金額確認時間及人數不足時的處理方式。
- 未確定分攤規則前，不得把動態估算呈現為最終應付金額。
- 建議首版由主揪自行收款，App 僅呈現費用及記錄收款狀態，不代收款、不預訂場地。

### 3.5 報名、候補與取消

- 尚有名額時加入正取，額滿時可加入候補；同一帳號不得重複報名或同時出現在兩份名單。
- 取消正取後，按候補順序遞補；取消候補時移出候補名單。
- 報名、取消及遞補須以具一致性保障的資料操作執行，避免多人同時操作造成超收。
- 取消前顯示確認與可能的費用影響；取消期限、逾期處理及主揪取消規則待確認。
- 介面須呈現操作成功、失敗及最新報名狀態。
- 本草案以候補機制取代歷史文件「額滿直接拒絕報名」的方向。

### 3.6 主揪管理與我的場次

- 主揪可查看正取與候補名單；建議提供出席及收款狀態記錄。
- 主揪可管理自己的場次，其他使用者不得修改場次或他人的出席／收款資料。
- 已確認（2026-11-14）：主揪在場次開始前可編輯所有欄位，即使已有人報名；總名額不得低於已約人數加正取人數。名額增加或已約人數減少時，候補依報名順序自動遞補。主揪可在開始前取消整場，取消後無法復原。尚無通知功能，場次頁以「主揪更新過場次資訊」標示異動。
- 場次編輯與取消須明確顯示狀態；已有報名後的費用、名額及時間變更規則待確認。
- 使用者能找到自己建立、已報名及候補中的場次。
- 場次異動與遞補需要讓相關使用者得知；Web 首版採站內提示、Email 或推播的範圍待確認，不直接沿用舊文件的全面 FCM 要求。

### 3.7 廣告與免費服務

- 建立場次、找場次及報名等核心功能維持免費。
- 建議於列表與詳情預留廣告位置，不遮擋費用、名單或操作按鈕，也不要求觀看廣告才可報名。
- 廣告未載入、被阻擋或服務尚未配置時，核心流程仍能正常操作。
- Web 與 iOS 分別整合適用的廣告服務；既有行動版廣告元件不可直接當作 Web 廣告方案。
- 開發與功能測試使用測試廣告或占位內容，正式投放另行配置。
- 曝光、點擊與收益統計以選定廣告平台的有效事件及報表為準，不以停留 30 秒自行視為有效廣告曝光。
- 廣告商、版位、隱私／同意流程與上線設定，於選定服務後另補實作規格。

## 4. 技術方向與目前銜接工作

- 延續既有 Flutter、Provider、GoRouter、Firebase Authentication 與 Firestore 架構，不因本次 SPEC 更新要求重寫狀態管理。
- Web Firebase 初始化已改用 build／run 時提供的 Dart define；實際 Firebase 專案、Google OAuth、索引與規則仍待測試專案驗證。
- Web 與行動廣告採平台分流；行動廣告初始化或版位載入失敗時不阻斷 App 啟動與核心流程。
- 現有資料集合為 `users`、`groups`、`events`；以此為銜接基礎，不依歷史文件改名為 `activities`。
- 場次模型已有獨立主揪識別、運動類型、地區、既有人數及兩種費用呈現；舊資料切換仍須依遷移指引執行。
- 登入、授權、容量限制及重要資料一致性須由後端／Firestore 規則等可信任機制保障，不能只依賴隱藏 UI 按鈕。
- 公開場次文件只保存報名人數；參與者 UID 與報名狀態存於私人參與者子集合。本人可讀自己的報名狀態，主揪可管理該場名單。舊版公開 UID 必須在切換新版前遷移並移除。
- 載入、空列表、找不到場次、權限不足及網路錯誤須有可理解的提示，適用時提供重試；球隊其他成員暱稱尚未接入，不得以虛構姓名呈現。

## 5. 驗證情境

第一階段以以下情境作為功能驗證基線，待決規則確認後再補完整驗收案例：

1. Web 可編譯及啟動，手機與桌面瀏覽器皆能完成核心操作。
2. 主揪發布一場總名額 10 人、既有 6 人的活動，顯示尚缺 4 人。
3. 另一帳號從分享網址進入，登入後能回到該場次並完成報名。
4. 依運動、地區及日期篩選，能找到符合條件的場次。
5. 多人同時搶最後一席時不超收，其餘依規則進入候補；重複點擊不重複報名。
6. 正取取消後第一位候補遞補，名額與名單同步更新；候補取消不影響正取。
7. 費用方案及預估／確定狀態明確，既有人數與主揪不重複計費或占位。
8. 非主揪不能修改他人場次及管理資料；未登入者不能執行報名等受保護操作。
9. 已取消、已開始或不存在的場次不接受新報名，並有明確提示。
10. Firebase 操作失敗與廣告載入失敗時不出現假成功，廣告異常不阻斷報名。
11. 直接開啟、重新整理及分享場次網址可正常運作。
12. 登入頁只有 Google 入口；首次登入建立資料，再次登入不重複建立或覆蓋暱稱。
13. 從場次登入後返回原場次；取消、失敗、重試、重新整理及登出均有正確狀態。

功能驗證之外，試用時觀察發布場次數、成功報名數、缺額補齊情況、取消與遞補情況，以及主揪對費用管理的回饋。量化門檻與蒐集方式尚待確認。

## 7. 實作前待確認事項

1. 費用：已確認（2026-11-14）由主揪於場次開始後手動確定每人最終費用（主揪或管理者可修改），建議金額為固定費用原價，或場租 ÷（主揪安排＋正取）人數無條件進位；確定後通知正取球友。
2. 報名：直接加入或主揪審核；是否允許代朋友報名及相關占位方式。
3. 取消與異動：取消期限、逾期處理、人數不足是否照常開打。（已有人報名後的變更方式已確認，見 3.6。）
4. 管理：已確認（2026-11-14）首版納入出席與收款標記（主揪與管理者可記錄）、主揪與管理者可在開始前移除參與者（正取被移除時候補自動遞補）及取消整場活動。
5. 通知：已確認（2026-11-14）採站內通知＋瀏覽器推播（FCM）。通知事件：候補遞補、主揪更新場次、場次取消、被移出名單、主揪確定費用。推播需在 Firebase Console 產生網路推播憑證（VAPID）並於 build 時帶入；未設定時僅站內通知。登入方式已確認僅使用 Google。
6. 試用範圍：優先地區、幣別、初期測試球友與驗證成功門檻。
7. 廣告：Web 服務商、首版正式投放或先預留版位，以及 iOS 的後續廣告方案。

## 8. 現況註記

截至 2026-09-30，Web 已有 Google 單一登入、公開場次瀏覽與篩選、分享連結、發布、兩種費用呈現、正取／候補／取消遞補、個人資料與「我的場次」頁。報名 UID 已改存於私人參與者子集合；取消與 FIFO 候補遞補改由 asia-east1 callable Cloud Function 執行。已新增舊場次遷移工具、規則與複合索引設定，但正式資料尚未遷移或部署。Firestore 規則與 Web/Functions 需在此資料模型變更後重新驗證；Web AdSense 與 iOS／Android AdMob 橫幅元件已預留設定入口。

近期維護另補上行動廣告初始化失敗時的降級處理、場次與球隊活動清單的錯誤重試，以及發布場次日期／時間選擇器的頁面存活檢查。球隊成員頁目前只顯示實際可得的成員數與管理員，不虛構其他成員姓名。README 已提供帶入 Firebase Web 設定值的正式 build 範例。2026-11-14 已在本機完成 Dart 格式化、Flutter 分析（無問題）、自動化測試、Functions 語法檢查、Firestore 規則模擬器測試及 Web 編譯，並修正主揪無法讀取報名名單的規則錯誤。

2026-11-14 新增主揪編輯與取消場次：編輯由 asia-east1 callable Cloud Function `updateEvent` 處理並在同一 transaction 內遞補候補；取消由 Firestore 規則限定只有主揪可在開始前將狀態改為已取消。

2026-11-14 主揪名單改為顯示報名者暱稱：報名時將暱稱寫入私人參與者文件的 `displayName`，Firestore 規則要求其等於報名者 `users` 文件中的暱稱，避免冒名；使用者修改暱稱時，以同一批寫入同步自己所有報名資料。遷移前的舊報名資料沒有暱稱，名單以「球友 N」顯示。球隊成員暱稱仍未接入。

2026-11-14 地區改為「縣市＋鄉鎮市區」下拉選單，發布與首頁篩選共用同一份清單；場次新增 `city` 欄位，首頁可依縣市或鄉鎮市區篩選。Firestore 規則與 `updateEvent` 要求地區全名以縣市開頭。

正式 Firebase 專案、Google 登入、索引、Functions 與網域尚未完成端到端驗證；既有公開場次資料須先以遷移工具移除 UID，再部署新版規則與程式。AdSense／AdMob 帳戶與正式版位 ID 尚未配置，廣告不會產生營收。費用確定方式、通知、出席／收款標記與取消政策仍待產品決策；完整球隊治理及 iOS 上架仍屬後續範圍。

本文件描述產品需求與規劃方向，不代表上述功能已完成或可直接上線。
